# Контекст проекта «Клевер» для Codex

## 1. Назначение документа

Репозиторий: `zhpchshts/telegram-predictor-bot`.

«Клевер» — Telegram-бот и Telegram Mini App для проведения конкурсов
прогнозов на спортивные и киберспортивные турниры в групповых чатах.

Проект работает в продакшене. Любые изменения должны учитывать существующие
данные, конкурсы, матчи, результаты и прогнозы пользователей.

В этом документе различаются три типа сведений:

* **фактическое текущее поведение** — то, как проект устроен сейчас по коду и
  тестам; само по себе оно не считается дефектом без отдельного продуктового
  решения;
* **обязательные продуктовые правила** — поведение, которое нужно сохранять,
  если задача явно не требует его изменить;
* **известные технические ограничения** — границы текущей реализации, которые
  нужно учитывать при будущих изменениях.

Код и актуальные тесты являются источником истины. Перед изменением логики
сначала изучай текущую реализацию и связанные тесты, а не основывайся только на
этом документе.

## 2. Технологический стек и фактическая архитектура

Стек проекта:

* Python;
* FastAPI;
* aiogram;
* SQLite;
* HTML/CSS/JavaScript для Telegram Mini App;
* Docker Compose;
* Nginx;
* Certbot.

Основные каталоги:

* `app/` — серверная логика, Telegram-бот, API, работа с БД, начисление баллов
  и фоновая публикация прогнозов;
* `tma/` — интерфейс Telegram Mini App без отдельного frontend build pipeline;
* `tests/` — автоматические тесты.

Фактическое текущее устройство:

* FastAPI, aiogram polling и воркер публикации прогнозов запускаются в одном
  приложении;
* Telegram Mini App — единственный полноценный пользовательский интерфейс;
* команды бота используются только для запуска приложения и служебных
  сценариев;
* создание конкурса через TMA поддерживает шаблоны Чемпионата мира 2026 и
  The International 2026 с отдельными правилами матчей, серий и начисления
  баллов;
* `initialize_database()` создаёт только актуальную схему из `app/database.py`;
  поддержки обновления исторических схем при запуске нет;
* `users` и `teams` являются глобальными сущностями БД, хотя конкурсы и основные
  пользовательские сценарии привязаны к Telegram-чатам;
* фундамент ролевой модели реализован на уровне Telegram-чата, но ограничение
  существующих операций по ролям пока не включено.

Обязательные продуктовые правила:

* не создавай параллельный полноценный интерфейс управления через команды или
  обычные сообщения Telegram;
* не добавляй Node.js-зависимости или отдельный frontend build pipeline без
  необходимости;
* не начинай крупную архитектурную перестройку без отдельной задачи.

## 3. Текущая продуктовая модель

### Чаты и конкурсы

Фактическое текущее поведение:

* конкурс принадлежит Telegram-чату;
* в одном чате может существовать несколько параллельных конкурсов;
* конкурсы бывают активными и завершёнными;
* после завершения конкурс перемещается в раздел завершённых и становится
  доступным только для просмотра;
* активный конкурс можно необратимо удалить через TMA вместе с его зависимыми
  данными;
* после удаления конкурса глобальные записи пользователей и команд остаются в
  БД;
* конкурс может быть связан с общим турниром: состав, матчи, все дедлайны,
  результаты матчей, чемпион и итоги швейцарского этапа синхронизируются между
  чатами, а прогнозы, рейтинг и публикации остаются отдельными по конкурсам;
* общими турнирами можно управлять только из глобального раздела TMA и только
  Telegram-пользователям из `SHARED_TOURNAMENT_ADMIN_IDS`; права администратора
  отдельного чата этого доступа не дают;
* эффективная роль пользователя имеет значение `telegram_admin`,
  `supermoderator` или `participant`;
* владелец и администраторы Telegram-чата определяются при каждом TMA bootstrap
  через `getChatAdministrators` и не сохраняются как назначения в БД;
* назначение супермодератора хранится на уровне Telegram-чата, действует до
  явного отзыва и сохраняет историю повторных назначений;
* Telegram-администраторы управляют активными назначениями через chat-level
  раздел TMA, не относящийся к отдельному конкурсу;
* нового супермодератора можно выбрать по точному положительному Telegram ID
  либо найти по точному `@username`, даже если он ранее не использовал Клевер;
  username разрешается через MTProto в стабильный Telegram ID, после чего
  локальный пользователь создаётся или обновляется;
* роль `telegram_admin` имеет приоритет над `supermoderator`, не удаляя и не
  изменяя локальное назначение;
* при недоступности Telegram-проверки возвращается отдельное состояние
  `unavailable`: активное назначение сохраняет роль `supermoderator`, а без него
  роль не подставляется;
* текущая принадлежность пользователя Telegram-чату не проверяется, поэтому
  выход, исключение или блокировка не отзывают локальное назначение;
* любой пользователь, получивший доступ к контексту независимого конкурса,
  по-прежнему может управлять настройками, матчами и результатами независимо от
  вычисленной роли; турнирные данные связанного конкурса локально не меняются.

Обязательные продуктовые правила:

* конкурс пока считается доверенным пространством участников чата;
* не подключай ролевую модель к блокировке операций и не добавляй новые
  ограничения доступа без отдельного согласования;
* не меняй необратимое удаление или правила завершения конкурса неявно — такие
  изменения требуют отдельной задачи.

### Матчи и противостояния

Фактическое текущее поведение:

* сохранённый статус матча имеет одно из значений:
  * `scheduled`;
  * `started`;
  * `finished`;
  * `cancelled`;
* при наступлении `starts_at_utc` матч активного конкурса автоматически и
  атомарно получает сохранённый статус `started`;
* переход `scheduled → started` выполняет lifecycle worker, а чтение активного
  конкурса дополнительно запускает scoped reconciliation для его матчей;
* закрытие прогнозов, доступность внесения результата и раскрытие истории в
  основном определяются сравнением текущего времени с `starts_at_utc`, с учётом
  сохранённого статуса;
* публичного API для ручного перевода матча в `started` или `cancelled` сейчас
  нет;
* матч, создаваемый через TMA, получает отдельную однораундовую сущность `tie`;
* матч активного конкурса можно необратимо удалить через TMA вместе с его
  результатом, прогнозами и начисленными баллами;
* сохранение результата переводит матч в `finished`; уже сохранённый результат
  можно исправить, после чего баллы пересчитываются.
* одинаковая неупорядоченная пара команд в одном общем турнире определяет один
  общий матч независимо от времени начала;
* общий матч материализуется отдельной локальной записью в каждом связанном
  конкурсе, поэтому прогнозы и начисления остаются изолированными по чатам;
* время общего матча атомарно меняется во всех связанных конкурсах только до
  текущего дедлайна; после дедлайна перенос и переоткрытие запрещены;
* результат и его исправления распространяются во все связанные конкурсы,
  включая завершённые, и пересчитывают локальные рейтинги;
* удаление общего матча необратимо удаляет его локальные копии, прогнозы и
  начисления во всех чатах; пересоздание образует новый матч с новым дедлайном.

Обязательные продуктовые правила:

* дедлайн подачи и изменения прогноза — время начала матча;
* после начала матча прогноз изменять нельзя;
* для завершённого матча указывается фактический итоговый счёт;
* для матчей плей-офф учитывается счёт после дополнительного времени, если оно
  проводилось;
* голы серии пенальти в счёт матча не добавляются;
* отдельно указывается команда, прошедшая дальше;
* не меняй эту модель на счёт после 90 минут без отдельного продуктового
  решения.

### Прогнозы матчей

Фактическое текущее поведение:

* прогноз счёта хранится в `match_predictions`;
* прогноз команды, которая пройдёт дальше, хранится отдельно в
  `tie_predictions`;
* при неничейном прогнозе TMA автоматически определяет прошедшую команду по
  прогнозируемому счёту;
* backend всё равно валидирует, что выбранная прошедшая команда является одной
  из команд матча и при неничейном счёте совпадает с победителем по счёту;
* прогнозы матчей не записываются в `event_log`;
* текущие шаблоны ориентированы на матчи плей-офф и серии с выбором команды,
  которая пройдёт дальше; обычный матч, где ничья является полноценным исходом
  без такого выбора, пока не реализован.

Обязательные продуктовые правила:

* при ничейном прогнозе пользователь обязан выбрать команду, которая пройдёт
  дальше;
* пока эта команда не выбрана, прогноз нельзя считать полностью сохранённым и
  интерфейс не должен подтверждать успешное автосохранение;
* режим обычных матчей, где ничья является полноценным исходом без выбора
  прошедшей команды, пока не реализован и не должен появляться неявно.

### Автосохранение

Фактическое текущее поведение:

* автосохранение применяется только к прогнозам матчей;
* сохранение считается завершённым после выбора счёта, если счёт неничейный и
  TMA автоматически определил прошедшую команду;
* при ничейном счёте сохранение считается завершённым только после выбора
  прошедшей команды;
* прогноз чемпиона сохраняется отдельным действием в интерфейсе.

Обязательные продуктовые правила:

* не добавляй отдельную обязательную кнопку «Сохранить» для прогнозов матчей,
  если это не требуется конкретной задачей;
* не превращай сохранение прогноза чемпиона в автосохранение неявно.

### Прогноз на чемпиона

Фактическое текущее поведение:

* настройка прогноза на чемпиона хранится на конкурсе;
* кандидаты формируются из глобальных команд, участвующих в матчах конкретного
  конкурса;
* пользователь создаёт или изменяет прогноз отдельным действием до дедлайна;
* текущий дедлайн можно изменить только до его наступления; новый дедлайн при
  изменении должен оставаться в будущем;
* фактического чемпиона можно указать после завершения всех матчей конкурса;
* исправление фактического чемпиона сразу меняет рассчитанный рейтинг.

Обязательные продуктовые правила:

* организаторы конкурса могут включить прогноз на чемпиона, задать дедлайн и
  количество баллов, а после окончания турнира указать фактического чемпиона;
* прогноз на чемпиона учитывается в рейтинге и в количестве рассчитанных или
  ещё не рассчитанных прогнозов;
* если прогноз на чемпиона включён, конкурс нельзя завершить без указанного
  фактического чемпиона.

### Прогноз на итоги швейцарского этапа

Фактическое текущее поведение:

* в конкурсе можно включить один составной прогноз на итоги швейцарского этапа;
* его список команд задаётся независимо от матчей конкурса и использует
  глобальные записи `teams`;
* настройки содержат дедлайн и положительные лимиты команд, проходящих напрямую
  и через элиминейшн-раунд; значения по умолчанию — `3 + 5`;
* участник одним явным действием сохраняет два непересекающихся набора команд
  точного настроенного размера; повторное сохранение атомарно заменяет весь
  прогноз;
* после первого пользовательского прогноза или внесения результата лимиты,
  список команд и состояние включения блокируются, но текущий дедлайн можно
  менять до его наступления; новый дедлайн должен оставаться в будущем;
* фактический результат можно внести после дедлайна и исправлять, пока конкурс
  активен; рейтинг пересчитывается немедленно на чтении;
* за команду и точный способ прохода начисляется 2 балла, за прошедшую команду
  с перепутанным способом — 1 балл, за вылетевшую или не выбранную команду —
  0 баллов; баллы за угаданный вылет не начисляются;
* баллы входят в `total_points`, но не образуют нового тай-брейкера;
* до дедлайна чужие прогнозы не раскрываются, после дедлайна видны оба набора,
  а после результата — разбивка баллов;
* включённый прогноз без фактического результата блокирует завершение конкурса;
* последующие матчи double elimination создаются и прогнозируются отдельно как
  обычные прогнозы на матчи.

Обязательные продуктовые правила:

* список кандидатов не должен зависеть от уже созданных матчей;
* одна команда не может одновременно находиться в двух категориях;
* дедлайн закрывает создание и изменение пользовательского прогноза;
* после наступления текущего дедлайна переносить его нельзя;
* не начисляй баллы за команды, которые участник не выбрал среди проходящих;
* не добавляй результаты швейцарского этапа в существующие спортивные
  тай-брейкеры и Telegram-публикации без отдельной задачи.

### Публикация прогнозов

Фактическое текущее поведение:

* публикация включается отдельно для каждого конкурса;
* публикации прогнозов, результатов и итогового рейтинга отправляются как
  Telegram Rich Messages, а списки участников отображаются нативными таблицами;
* после включения обрабатываются только матчи, начинающиеся позже момента
  включения настройки;
* публикуются прогнозы только конкретного начавшегося матча;
* отправленные части сообщения и завершённая публикация фиксируются в БД;
* защита от последовательных повторов и продолжение после частично
  отправленного многочастного сообщения реализованы;
* полная защита от одновременной конкурентной работы нескольких процессов не
  гарантирована текущей реализацией;
* итоговая публикация показывает единственного победителя;
* при равенстве итоговых очков в ней указывается только причина решающего
  тай-брейка, без вывода полного правила.

Обязательные продуктовые и технические правила:

* публикация прогнозов должна относиться только к конкретному начавшемуся матчу,
  а не ко всем прогнозам конкурса;
* одна публикация не должна дублироваться при повторном запуске обработчика или
  воркера;
* при изменении механизма публикаций обязательно учитывай конкурентный запуск
  нескольких процессов, повтор после сбоя и частично отправленные сообщения;
* для усиления гарантий используй явную атомарную защиту, а не предположение об
  единственном процессе.

## 4. Начисление баллов

Фактическое текущее поведение:

* за счёт матча выдаётся только одна наиболее приоритетная награда:
  * точный счёт — 3 балла;
  * правильная разница мячей — 2 балла;
  * правильный исход — 1 балл;
* отдельно начисляется 1 балл за правильно выбранную команду, прошедшую дальше;
* согласно текущей реализации этот дополнительный балл начисляется не только
  для ничейного прогноза: при неничейном прогнозе прошедшую команду заранее
  определяет прогнозируемый счёт;
* отдельно могут начисляться настроенные баллы за правильно угаданного
  чемпиона;
* исправление результата матча удаляет прежние начисления и пересчитывает их
  заново.

Обязательные продуктовые правила:

* не меняй значения баллов, порядок приоритетов, правила ничьих или учёт
  прошедшей команды без явного требования;
* перед изменением формулы изучи `app/scoring_service.py`, связанные запросы в
  `app/contest_service.py` и тесты;
* не начинай переработку системы начисления баллов без отдельной задачи.

## 5. Рейтинг и история прогнозов

Фактическое текущее поведение:

* основной критерий рейтинга — итоговое количество баллов;
* рейтинг всегда присваивает участникам уникальные последовательные места
  `1, 2, 3, ... N`;
* при равенстве итоговых баллов последовательно учитываются количество наград
  за точный счёт, правильную разницу мячей и правильный исход, затем количество
  правильно выбранных прошедших команд при ничейном прогнозе счёта и правильно
  угаданный чемпион;
* награда за прошедшую команду при неничейном прогнозе счёта не входит в
  соответствующий тай-брейкер, хотя продолжает учитываться в итоговых баллах;
* правильно угаданный чемпион является тай-брейкером при любом настроенном
  количестве баллов за него, включая ноль;
* при полном равенстве спортивных показателей используется стабильный
  детерминированный жребий, различающийся для разных конкурсов и не зависящий от
  имени участника или порядка чтения данных;
* количество рассчитанных и ещё не рассчитанных сохранённых прогнозов
  отображается как информационный показатель и не является тай-брейкером;
* количество прогнозов и время их сохранения не влияют на место;
* рейтинг показывает итоговые баллы, количество рассчитанных и ещё не
  рассчитанных прогнозов, историю закрытых прогнозов на матчи и прогноз
  чемпиона после его закрытия;
* прогнозы будущих матчей других участников до дедлайна в истории не
  раскрываются;
* отменённые матчи не учитываются в количестве сохранённых или рассчитанных
  прогнозов.

Формат количества прогнозов учитывает рассчитанные и ещё не рассчитанные
сохранённые прогнозы на матчи и долгосрочные прогнозы:

* `Прогнозов: 8+1 из 9`;
* `Прогнозов: 8+2 из 10`.

Здесь первое число — количество прогнозов, для которых уже внесён фактический
результат и рассчитаны баллы, число после `+` — количество сохранённых, но ещё
не рассчитанных прогнозов, последнее число — сумма этих двух значений. Каждый
долгосрочный прогноз считается одной единицей.

Обязательные продуктовые правила:

* сохраняй последовательность тай-брейкеров: итоговые баллы, точные счета,
  правильные разницы, правильные исходы, прошедшие команды только при ничейных
  прогнозах счёта, угаданный чемпион, детерминированный жребий;
* не используй количество рассчитанных или ещё не рассчитанных прогнозов, время
  прогнозирования, имя или фамилию как тай-брейкер;
* не раскрывай прогнозы участников до закрытия соответствующего дедлайна;
* при изменении рейтинга одновременно проверяй итоговые баллы, места, количество
  рассчитанных и ещё не рассчитанных прогнозов и историю прогнозов.

## 6. Авторизация и модель доступа

Фактическое текущее поведение:

* Telegram `initData` передаётся в `X-Telegram-Init-Data`;
* подпись `initData` проверяется с использованием токена бота;
* `initData` принимается не старше 24 часов;
* контекст чата извлекается из подписанного launch token, создаваемого командой
  `/app` в групповом чате;
* launch token действует 30 дней;
* текущая авторизация проверяет Telegram-пользователя, подпись `initData` и
  подпись/срок launch token;
* фактическое текущее членство пользователя в Telegram-чате не проверяется;
* TMA bootstrap получает актуальный список владельца и администраторов через
  `getChatAdministrators`, не используя `getChatMember`;
* каждый endpoint управления супермодераторами повторно проверяет вызывающего
  пользователя через `getChatAdministrators` и работает по fail-closed модели;
* разрешение точного username выполняет общий для процесса клиент
  `Telethon==1.44.0`, авторизованный тем же `BOT_TOKEN` как бот, а не как
  пользовательский аккаунт; приём updates у этого клиента отключён;
* MTProto-клиент использует `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` и постоянную
  сессию по `TELEGRAM_MTPROTO_SESSION_PATH`; отсутствие или временная ошибка
  этой интеграции отключает только поиск новых пользователей;
* MTProto session-файл содержит чувствительные данные авторизации, хранится вне
  Git (в production — внутри постоянного `/data`) и не должен попадать в логи
  или review-артефакты;
* внутренние назначения супермодераторов действуют до явного отзыва независимо
  от текущего членства пользователя в Telegram-чате;
* приоритет эффективных ролей: `telegram_admin`, затем `supermoderator`, затем
  `participant`;
* временная ошибка Telegram API представляется как `verification_status =
  unavailable`, не маскирует ошибки БД и не отменяет локальное назначение;
* feature flag `ROLE_ENFORCEMENT_ENABLED` передаётся в bootstrap, по умолчанию
  равен `false` и пока не блокирует операции даже при значении `true`.

Обязательные продуктовые правила:

* не доверяй идентификаторам пользователя или чата, переданным клиентом вне
  проверенного Telegram-контекста;
* управление ролью `supermoderator` доступно только подтверждённому владельцу
  или администратору текущего Telegram-чата; блоку `access` на клиенте для
  авторизации доверять нельзя;
* username используется только для актуального разрешения пользователя и не
  является ключом назначения: назначение всегда привязано к стабильному
  Telegram ID через внутренний `users.id`;
* назначение по Telegram ID не требует MTProto и допускает локального
  пользователя без имени и username; отсутствующие профильные данные нельзя
  заменять вымышленными значениями;
* членство целевого пользователя в Telegram-чате не проверяется, а
  администратор отвечает за корректность выбора; назначение действует до
  явного отзыва;
* не добавляй роль `moderator`, управление ролями через Telegram-команды или
  ограничение существующих операций без отдельной задачи;
* проверка членства в чате требует отдельного продуктового решения и обновления
  backend, TMA и тестов.

Известное техническое ограничение:

* действующий launch token является достаточным источником контекста чата после
  успешной проверки `initData`; принадлежность пользователя чату отдельно не
  подтверждается; пользователь с переданной действующей ссылкой может открыть
  конкурс и участвовать независимо от членства в исходном чате.

## 7. База данных, миграции и сохранность данных

Фактическое текущее поведение:

* используется SQLite с включёнными foreign keys;
* актуальная схема создаётся через `CREATE ... IF NOT EXISTS`;
* `initialize_database()` не выполняет inline-миграции, backfill или
  пересоздание таблиц и не поддерживает запуск поверх исторической схемы;
* назначения супермодераторов хранятся в `supermoderator_assignments`; частичный
  уникальный индекс не допускает двух активных назначений одного пользователя в
  одном чате, а отозванные записи сохраняются как история;
* отдельной таблицы версий миграций и внешнего migration framework нет;
* изменения матча, результата, настроек конкурса, чемпиона и завершения в
  основном фиксируются в `event_log`;
* обычное создание или изменение прогноза матча в `event_log` не записывается;
* удаление конкурса каскадно удаляет его зависимые данные, но не удаляет
  глобальных пользователей и команды.

Обязательные технические правила для продакшена:

* не удаляй и не сбрасывай существующие данные;
* не предлагай пересоздание продовой базы;
* не выполняй массовые исправления продовых данных без отдельного согласования
  и резервной копии;
* изменение схемы после создания новых ценных данных требует отдельного
  согласованного плана миграции или контролируемого reset с архивной копией;
* не добавляй постоянный код совместимости со старой схемой в
  `initialize_database()` без отдельного решения;
* не меняй семантику существующих полей без явного плана переноса данных;
* не сохраняй устаревшие API-контракты неявно: изменение контракта должно быть
  явным, согласованным и одновременно отражённым в backend, TMA и тестах;
* не допускай потери прогнозов, результатов, рейтингов и истории;
* не считай пользовательское удаление через TMA разрешением на произвольную
  очистку или пересоздание продовых данных.

## 8. Конкурентность и идемпотентность

Фактическое текущее поведение:

* создание конкурса и матча использует idempotency key и отдельные таблицы
  запросов;
* повтор ключа с теми же данными возвращает ранее созданную сущность;
* повтор ключа с другими данными отклоняется;
* сохранение прогнозов выполнено через `UPSERT`;
* сохранение завершённой публикации и отдельных частей сообщения защищает от
  последовательной повторной обработки;
* текущий механизм публикации не даёт полной гарантии exactly-once при
  одновременной работе нескольких процессов.

Обязательные технические правила:

* учитывай возможный параллельный запуск нескольких экземпляров;
* учитывай повторный запуск после сбоя и повторную обработку одной записи;
* учитывай изменение данных между чтением и записью;
* для операций, которые должны выполняться один раз, используй транзакции,
  условные `UPDATE`, уникальные ограничения или другую явную атомарную защиту;
* не считай один процесс или один воркер гарантированно единственным;
* при изменении публикаций отдельно проверяй последовательный повтор, частичную
  отправку и конкурентный запуск.

## 9. API и Telegram Mini App

При изменении API:

* проверяй все места использования endpoint в `tma/`;
* сохраняй существующий формат ответа либо обновляй backend, frontend и тесты
  одновременно;
* не удаляй поля ответа без отдельной необходимости;
* валидируй входные данные на сервере, даже если они валидируются в интерфейсе;
* не доверяй данным клиента;
* учитывай Telegram `initData`, launch token и текущую модель авторизации;
* помни, что публичного endpoint для установки `started` или `cancelled` сейчас
  нет.

При изменении TMA:

* сохраняй совместимость с Telegram WebView;
* учитывай мобильные размеры экрана и safe area;
* не полагайся только на `hover`;
* не добавляй Node.js-зависимости без необходимости;
* не создавай отдельный frontend build pipeline, если задачу можно решить в
  текущей структуре;
* не дублируй бизнес-логику backend на клиенте;
* после сохранения интерфейс должен отображать фактический ответ сервера;
* сохраняй автосохранение матчевых прогнозов и отдельное действие для прогноза
  чемпиона, если задача явно не меняет это поведение;
* TMA должен оставаться единственным полноценным пользовательским интерфейсом.

## 10. Тестирование и проверки

После изменений должны проходить:

```bash
python -m ruff format --check .
python -m ruff check .
python -m pytest
```

Количество тестов со временем меняется, поэтому ориентируйся на полный успешный
прогон, а не на фиксированное число.

Для новой бизнес-логики добавляй тесты как минимум на:

* основной успешный сценарий;
* граничные состояния;
* запрещённые переходы;
* повторный вызов или идемпотентность, если применимо;
* конкурентный сценарий, если операция должна выполняться один раз;
* сохранение существующего поведения и данных.

При исправлении дефекта:

1. найди первопричину;
2. добавь или обнови тест, воспроизводящий проблему;
3. внеси минимальное исправление;
4. проверь соседние актуальные сценарии и заявленный API-контракт.

Не изменяй тесты только ради того, чтобы скрыть регрессию. Не маскируй ошибки
широкими `try/except`, пустыми обработчиками исключений или неявными значениями
по умолчанию.

## 11. Git и деплой

Продакшен расположен на VPS:

```text
/opt/telegram-predictor-bot
```

Продакшен запускается через Docker Compose. Внешний health endpoint:

```text
http://127.0.0.1:8001/health
```

Для штатного деплоя используется:

```bash
/opt/deploy-telegram-predictor-bot.sh
```

Скрипт:

* создаёт резервную копию БД;
* выполняет `git pull --ff-only`;
* собирает Docker-образ;
* запускает форматирование, линтер и тесты;
* пересоздаёт контейнер;
* выводит статус и последние логи.

Git-команды в `/opt/telegram-predictor-bot` нельзя выполнять от `root`, поскольку
репозиторий принадлежит пользователю `reminderbot`. При необходимости ручной
Git-команды используй:

```bash
runuser -u reminderbot -- git -C /opt/telegram-predictor-bot <command>
```

Не добавляй репозиторий в глобальный `safe.directory` для root как штатное
решение.

Проверки внутри Docker должны запускаться через
`docker compose run --rm --no-deps` с переменными:

```text
BOT_TOKEN=dummy
PYTHONPATH=/app
```

Не выполняй деплой, не изменяй продовые данные и не коммить изменения без прямой
команды пользователя.

## 12. Текущая стадия и порядок работы

Проект уже запущен и используется. До окончания текущего чемпионата мира
плановые продуктовые доработки отложены. Приоритет — стабильность продакшена и
исправление реальных проблем.

Без отдельной задачи не начинай:

* ролевую модель;
* крупный редизайн или архитектурный рефакторинг;
* режим группового этапа или обычных матчей с полноценной ничьей;
* автоматическую загрузку матчей из внешних источников;
* переработку системы начисления баллов.

Для каждой задачи:

1. изучи связанные файлы, модели БД, API, TMA и тесты;
2. зафиксируй фактическое текущее поведение отдельно от желаемого изменения;
3. определи минимальный набор изменений;
4. проверь риски для существующих данных и продакшена;
5. внеси изменения непосредственно в репозиторий;
6. добавь или обнови тесты;
7. запусти форматирование, линтер и полный набор тестов;
8. покажи, что изменено, какие файлы затронуты, какие проверки выполнены, есть
   ли миграция и нужны ли действия перед деплоем.

Не утверждай, что проблема исправлена, если соответствующий сценарий не проверен
тестом или фактическим запуском. Не называй существующее поведение дефектом, если
по нему не принято отдельное продуктовое решение.
