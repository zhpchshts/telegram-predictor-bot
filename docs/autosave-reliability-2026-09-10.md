# Проверка автосохранения — 10 сентября 2026

Исполняемые браузерные сценарии проверяют исходный Mini App, настоящий FastAPI
API и отдельную временную SQLite-базу. Проверки сравнивают статус интерфейса с
сохранённым прогнозом. Внешние Telegram-вызовы и фоновые воркеры не запускаются.

## Воспроизведённые ошибки и исправления

| Сценарий | До исправления | После исправления |
| --- | --- | --- |
| Подтверждён A, сервер сохранил B, ответ потерян, участник вернул A | Интерфейс сообщал «Сохранено», в БД оставался B | После неопределённого результата A отправляется заново. Работает для счёта, прохода пары, чемпиона и этапа, включая очистку до исходного `0+0`. |
| Переход на другую вкладку; отправка и автоматический повтор завершились сетевой ошибкой | Последний снимок удалялся, повторное открытие показывало старый прогноз | Снимок остаётся в памяти страницы до подтверждения, нового выбора или окончательного отказа API. |
| После перехода пришёл HTTP 200 с некорректным прогнозом | Очередь уже удаляла снимок, форма обнаруживала ошибку без возможности автоматического повтора | Валидатор выполняется внутри очереди до подтверждения и повторно используется при повторе. |
| Выбор команды, проходящей двухматчевую пару | API возвращал HTTP 422 из-за лишнего `isReady` | Отправляется только предусмотренный API `predicted_advancing_team_id`. |

При истечении дедлайна неподтверждённое сохранение теперь явно называется
неподтверждённым. Поздний корректный ответ обновляет статус. HTTP 409 закрывает
форму и не переоткрывает прогноз. Окончательные ошибки вроде HTTP 404 после
удаления матча очищаются после отображения, чтобы не блокировать последующее
открытие оставшегося конкурса. Сетевые ошибки, некорректные ответы, HTTP 408,
429 и 5xx сохраняют снимок для следующей попытки.

## Проверки

- Исходный набор до изменений: 886 тестов прошли.
- Добавлено 42 браузерных сценария: 18 для матчей и переходов, 24 для чемпиона,
  общего этапа и прохода пары.
- Итоговый `python -m pytest -q --tb=short`: **928 passed**, включая браузерные
  проверки в Chromium, за 128,01 с. Отдельный запуск с `TMA_TEST_BROWSER=webkit`:
  **42 passed** за 79,09 с.
- `python -m ruff format --check .`, `python -m ruff check .`,
  `node --check tma/app.js` и `git diff --check` прошли.
- На неизменённых файлах `tma/` из исходного коммита `36544db` выбранные
  регрессионные сценарии дали 12 ожидаемых падений и 2 успешных проверки.
  Проверка выполнялась с отдельной копией static assets, без отката рабочей
  директории.
- Проверяются потеря ответа до/после записи, быстрые изменения, переходы,
  таймаут ожидания, некорректное подтверждение, события фона и возвращения,
  отправка перед дедлайном, поздний ответ, серверный отказ, ничья с выбором
  прошедшего, заполнение `8+12`, очистка этапа и счёт ответной игры после
  закрытия прогноза на проход.
- Стенд использует ширину экрана 390 px; CI запускает его отдельно в Chromium
  и WebKit. Playwright установлен только как дополнительная тестовая зависимость.
- Время жизни синхронного Playwright ограничено модулем тестов, чтобы его
  event loop не мешал существующим проверкам с `asyncio.run()`.

Установка, команды и получение трасс описаны в
[`tests/browser/README.md`](../tests/browser/README.md).

## Границы изменения

Схема БД и API-контракты не изменены, миграция не нужна. Исторические прогнозы,
формулы баллов, дедлайны и права доступа сохранены. Frontend остаётся статическим.

Очередь хранится в памяти открытой страницы. Это не offline-хранилище: полная
перезагрузка страницы или завершение процесса Telegram могут удалить ещё
неотправленный снимок. События `pagehide`, `pageshow` и `visibilitychange`
проверяются в браузере явно; физическое устройство и завершение приложения ОС
не эмулируются. Локальные тесты не заменяют наблюдение после будущего деплоя.

Коммит и деплой не выполнялись; изменения production-данных не производились.
